A [git worktree](https://git-scm.com/docs/git-worktree) is a second working
folder for the same repository, with its own branch checked out. You can
work on a fix in one while a long build or a half-finished change sits in the
other, without stashing or switching branches.

tt-git can create a new branch straight into a worktree, list your
worktrees, open one in place of the repository you're in, and remove the
ones you're done with.

## Creating a branch in a worktree

<Steps>

1. Select where the branch should start: a commit in the graph, a branch in
   the branch list, or a tag on the Tags tab.

2. Press <kbd>n</kbd>. The **New branch** box opens on its *Branch* tab.

3. Press <kbd>tab</kbd> to switch to the *Worktree* tab. The line under the
   name shows where it will go, for example
   `checked out in .worktrees/fix-login`.

4. Type the branch name and press <kbd>enter</kbd>.

</Steps>

<Screenshot name="worktree-dialog" alt="The New branch dialog with Worktree selected and the worktree path shown" />

tt-git runs `git worktree add -b <name> .worktrees/<name> <start>`. Your
current checkout stays as it was: you stay on the same branch with the same
files. The new branch appears in the branch list and the graph.

On the *Branch* tab instead, `enter` creates the branch and switches to it
here, like `git switch -c`.

## Where worktrees go

Worktrees go in a `.worktrees` folder at the top of your main checkout, one
folder per branch:

```
my-project/
├── .worktrees/
│   ├── fix-login/
│   └── spike-cache/
├── src/
└── ...
```

When tt-git makes the first one, it adds `/.worktrees/` to the repository's
`.git/info/exclude`, so the folder never shows up as untracked. That file is
local to your clone and isn't committed. Creating a worktree from inside
another worktree still puts it in the main checkout's `.worktrees/`.

## The Worktrees tab

The branches pane gets a **Worktrees** tab as soon as the repository has a
worktree besides the main one. It's the last tab: press <kbd>3</kbd>, then
<kbd>[</kbd> from the Branches tab (or <kbd>]</kbd> until you reach it), or
click its name in the title.

```
* .                    main                  main · clean  1.2 GB
  .worktrees/fix-login fix-login                3 changed 48.3 MB
  .worktrees/review    (detached 1a2b3c4)  locked · clean 47.9 MB
```

<Screenshot name="worktrees-tab" alt="The Worktrees tab listing the main worktree and two linked ones, with their branches, how many files have changes and how much disk space each takes" />

Each row shows:

- `*` on the worktree tt-git is running in.
- Its folder, as a path from the current directory: `.` for the worktree
  you're in, `.worktrees/fix-login` below it, `../..` from a linked worktree
  back to the main one. If you started tt-git outside the worktree it runs
  in, paths are from that worktree's root. A worktree on another drive shows
  in full.
- What it has checked out: a branch, or `(detached <commit>)`.
- Its state: `main` for the main worktree, `locked` if it was locked with
  `git worktree lock`, `missing` if its folder is gone, and how many files
  have uncommitted or untracked changes (`clean` for none). The counts are
  worked out in the background each time you open the tab and when the
  branches reload, so `…` shows until they're in.
- How much disk space its folder takes, ignored files like build output
  included. The main worktree's size leaves out the worktrees inside it, so
  nothing is counted twice. Sizes are measured in the background when you
  open the tab and when a worktree is added or removed; `…` shows until
  they're in.

The pane's bottom border shows the total for every worktree, like
`total 1.3 GB`.

Moving the selection also selects the worktree's commit in the graph.
<kbd>/</kbd> filters by path, and <kbd>c</kbd> copies the selected
worktree's absolute path, with `\` separators on Windows.

## Opening a worktree

Select a worktree and press <kbd>enter</kbd> (or <kbd>space</kbd>). tt-git
closes the repository it's in and opens that worktree in the same terminal,
as if you'd started `tt-git` there: the panes start over, the file watcher
follows the new folder, and plugins restart (their startup commands run
again and they get `repo.opened` for the new path). tt-git also changes its
working directory to the worktree, so it doesn't hold the old folder open.
The plugin API socket gets a new address, so a plugin process still running
from before can't reach the new one. To go back, open the main worktree the
same way.

It won't open:

- the worktree you're already in;
- one whose folder is gone (remove it instead);
- anything while a git command it started is still running (it asks you to
  wait).

You can still open a worktree in a second tt-git, side by side with the
first:

```sh
tt-git .worktrees/fix-login
```

Everything that lives in `.git` is shared between worktrees: commits,
branches, tags, remotes, stashes and config, including the
[base branch](/panes/merged-unmerged/#the-base-branch) you picked. A commit
in one shows up in the other's graph right away. The checked-out branch, the
staged changes and any merge or rebase in progress are separate.

<Aside type="caution">
	Git only lets a branch be checked out in one worktree at a time. Checking
	out `fix-login` in your main checkout fails while `.worktrees/fix-login`
	has it.
</Aside>

## Removing a worktree

On the Worktrees tab, select the worktree and press <kbd>d</kbd>. tt-git
asks first (**Remove worktree**), then runs
`git worktree remove <path>`: the folder is deleted, ignored files like build
output included, and git forgets the worktree. Its branch stays; delete it
from the Branches tab once it's merged.

<Screenshot name="worktree-remove" alt="The Remove worktree dialog, saying the branch stays and that it will ask again if there are changes" />

If the worktree has uncommitted or untracked changes, git refuses, and
tt-git asks again (**Uncommitted changes**) before running
`git worktree remove --force`, which deletes them for good. Answer
<kbd>n</kbd> to keep everything as it was.

tt-git won't remove:

- the main worktree;
- the worktree it's running in. Open another one first;
- a locked worktree. Unlock it with `git worktree unlock <path>` first.

A worktree whose folder you already deleted by hand shows as `missing`;
<kbd>d</kbd> on it drops it from git's list.

<Aside>
	On Windows, a folder that a program has open (an editor, a terminal whose
	current directory is inside it, a running build) can't be deleted, and the
	removal fails with git's error. Close it and press <kbd>d</kbd> again.
</Aside>

## A new worktree from the tab

<kbd>n</kbd> on the Worktrees tab opens **New branch** already on its
*Worktree* tab, starting from the selected worktree's branch (or its commit,
if it's detached).

## Keys

On the Worktrees tab:

| Key | Does |
|---|---|
| <kbd>enter</kbd> <kbd>space</kbd> | Open the worktree here, in place of this one |
| <kbd>n</kbd> | New branch in a new worktree, from the selected one |
| <kbd>d</kbd> | Remove the worktree (asks; asks again before `--force`) |
| <kbd>c</kbd> | Copy its absolute path |
| <kbd>/</kbd> | Filter as you type |
| <kbd>]</kbd> <kbd>[</kbd> | Next / previous tab |

The tab has its own key context, `worktrees`, which doesn't fall back to the
branches keys. See [Key bindings](/configuration/keys/#contexts).
