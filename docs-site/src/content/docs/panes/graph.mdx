The graph is tt-git's main view. It shows the history of every branch, remote branch and tag as one
GitLens-style graph, newest commit first, with one row per commit. Branches keep their column from
top to bottom, so you can follow a line by eye. From here you open a commit's details, filter the
history down to one author or one file, and start a branch, merge, rebase, cherry-pick or revert at the
selected commit. Press <kbd>1</kbd> to focus it from anywhere.

Working on one part of a large repository, such as a project in a monorepo or the docs? Start tt-git
in its folder and press <kbd>.</kbd> to [narrow the graph to it](#narrowing-to-the-folder-you-started-in).

<Screenshot name="graph-overview" alt="The graph pane with its title, lanes, badges, subjects, author and date columns called out" />

## What it shows

Each row is one commit:

```text
●    [side] side experiment                                   Test User      2h b66
◉─╮   main  <v1.0> Merge 'feature'                            Test User      3h 59f
│ ●  [feature] feature work                                   Test User      1d 788
● │  main work                                                Test User      1d f75
●─╯  base                                                     Test User      2d b29
```

From left to right:

- **Lanes**: where the commit sits in the history, and how it connects to its parents.
- **Badges** for the branches and tags that point at it.
- **The subject**, the first line of the commit message.
- **The author**, **how long ago** it was committed (`now`, `5m`, `3h`, `2d`, `3w`, `4mo`, `2y`) and
  **the short hash**.

On a narrow pane the author moves ahead of the other columns, so the subject stays readable.

Merge commits are dimmed: their subject, author, date and hash are drawn in gray, so the commits
that did the work stand out. Their badges and the `◉` in the lanes keep their colors.

The title tells you what you're looking at: `Graph [all] 12/4031` means every branch is shown and the
12th of 4,031 loaded commits is selected. A filter adds to it, for example
`Graph [all · author Ada · folder src/] 3/120` (a single file reads `file src/main.rs`). While a load is running the title ends in `loading…`.

<Aside type="tip">
  The graph follows your selection in the other panes: pick a branch or a tag in the
  [branches pane](/panes/branches/) and the graph jumps to its commit.
</Aside>

## Reading the lanes

<Screenshot name="graph-lanes" alt="A close-up of graph lanes showing a commit, a merge, a lane ending and a lane opening" />

Every line of history has its own column and color, and keeps that column for as long as it runs.
Branches go straight down instead of shifting sideways as other branches start and end.

| Glyph | Means |
|---|---|
| `●` | A commit |
| `◉` | A merge commit (more than one parent) |
| `│` | A line of history passing through this row |
| `─╯` | A line ending here: it joins this commit |
| `─╮` | A merge opening a new line for its other parent |
| `…` | More lanes than fit (see `max_lanes` below) |

A commit with nothing above it in its column is a branch tip. Each new tip and each merge's extra
parent gets the next of eight colors.

Only the first 16 lanes are drawn; wider histories collapse into `…`. You can change that with
`max_lanes` in the [configuration file](/configuration/).

### Hiding the lanes

Press <kbd>L</kbd> to hide the lanes. Each row then starts with its badges and subject, and the
subject gets the room the lanes took. Press <kbd>L</kbd> again to bring them back. The commits and
their order stay the same; only the drawing goes.

To start with the lanes hidden, set `lanes = false` under `[graph]` in the
[configuration file](/configuration/).

## Branch and tag badges

<Screenshot name="graph-badges" alt="A close-up of the badges for the checked-out branch, a local branch, a remote branch and a tag" />

Badges sit between the lanes and the subject:

| Badge | Means |
|---|---|
| ` main ` on green | The branch you have checked out |
| ` HEAD ` on red | A detached HEAD |
| `[feature]` (green) | A local branch |
| `[origin/main]` (magenta) | A remote branch |
| `<v1.0>` (yellow) | A tag |

Symbolic refs like `origin/HEAD` are left out, since they only repeat another badge. When a row is
too narrow for everything, badges are dropped before the subject is.

## All branches or just the current one

Press <kbd>a</kbd> to switch between two views:

- **all** shows every branch, remote branch and tag.
- **current** shows only `HEAD` and its upstream, so you can see what you'd push or pull without the
  rest of the repository in the way.

The title shows which one you're in: `Graph [all]` or `Graph [current]`. To leave the upstream out of
the current view, set `current_includes_upstream = false` in the [configuration file](/configuration/).

The [Unmerged and Merged tabs](/panes/merged-unmerged/) of the branches pane use the graph to show a
single branch. While they do, the title shows that branch's name, and <kbd>a</kbd> goes back to the
full graph.

You don't have to leave the graph to get there. With the graph focused, <kbd>]</kbd> and
<kbd>[</kbd> (or <kbd>&#125;</kbd> and <kbd>&#123;</kbd>) step the branches pane to its next or
previous [tab](/panes/branches/#the-tabs), as they do in the branches pane itself. Focus stays on the
graph, so you can flip to **Unmerged** or **Merged** and watch the graph follow.

## Narrowing to the folder you started in

<Aside type="tip" title="One project in a shared repository">
  Start tt-git inside a folder and press <kbd>.</kbd>. The graph and Status show only that folder's
  history and changes, and everything else in the repository gets out of the way.
</Aside>

Many repositories hold more than one thing, and most of their commits aren't about the part you're
working on. Start tt-git in that part's folder, such as `apps/web/`, and press <kbd>.</kbd> in the
graph to see only the commits that changed something under it, as `git log -- apps/web/` would.
Press <kbd>.</kbd> again to see everything.

```sh
cd apps/web && tt-git     # then press .
tt-git apps/web           # the same, without changing directory
```

### When it helps

| You're working on | Start tt-git in | You see |
|---|---|---|
| **One project in a monorepo** | `apps/web/`, `services/billing/`, `packages/ui/` | The commits for your project, not the dozens a day that land in its neighbors. What changed since you last pulled, who's been working on it, and which commit broke it. Status lists only your project's files. |
| **Documentation** | `docs/`, `docs-site/` | Every docs commit on its own, even when most of them were part of a code change: what was written for the last release, a page's history, and which docs a feature branch touched. |
| **A Storybook or design system** | `.storybook/`, `src/stories/`, `packages/design-system/` | The commits to your stories and their config, so you can see what changed in the component library without reading through app work. |
| **Infrastructure or config** | `infra/`, `deploy/`, `.github/` | Every change to your pipelines and deployment config, in order, for when you need to know what changed before something broke. |

Storybook stories often sit next to their components rather than in one folder. If yours do, narrow
to the component folder instead, or use <kbd>f</kbd> to pick any folder or file.

### How it behaves

- The title shows it: `Graph [all · folder apps/web/]`.
- An author filter stays set when you press <kbd>.</kbd>, so you can see one person's commits to
  your project.
- The [Status](/panes/status/#narrowing-to-a-folder) pane narrows to the same folder, and
  <kbd>.</kbd> works there too. Status is narrowed whenever the graph's filter is the folder you
  started in, however you set it: with <kbd>.</kbd>, by picking `current folder` in
  **Filter graph**, or at startup.
- <kbd>esc</kbd> in the graph (with details hidden) clears it, like any filter.
- Started at the top of the repository, there's no folder to narrow to, and <kbd>.</kbd> says so.
  Use <kbd>f</kbd> to filter by any folder.

To start narrowed every time, set
[`filter_to_cwd = true`](/configuration/#graph) under `[graph]`. `tt-git --filter-to-cwd` and
`tt-git --no-filter-to-cwd` turn it on or off for one run; see [CLI](/reference/cli/).

The lanes work as for any [file filter](#filtering-by-author-or-file): each commit links to the
nearest earlier commit that also changed the folder. Merges that brought no change to the folder
are left out, as `git log` does by default.

## Filtering by author or file

<Screenshot name="graph-filter" alt="The Filter graph popup listing authors with their commit counts" />

Press <kbd>f</kbd> to open **Filter graph**. It has two tabs, **Author** and **File**; <kbd>tab</kbd>
switches between them. You can set one or both, and a commit has to match both.

<Steps>

1. Press <kbd>f</kbd>.
2. Type part of a name or path. The list narrows as you type.
3. Pick an entry with <kbd>↑</kbd> <kbd>↓</kbd>.
4. Press <kbd>enter</kbd>. The graph reloads with only the matching commits.

</Steps>

With the mouse, click an entry to filter by it straight away, or click **Author** or **File** to
switch tabs. The wheel moves the selection, and a click outside the popup closes it without
changing the filter.

- **Authors** are listed with the most commits first. Each person appears once, even if they've
  committed under several email addresses, as long as your `.mailmap` says they're the same person.
- **Files** lists every tracked file, with each folder listed just before the first file in it. Pick
  a folder, such as `src/components/`, to see every commit that touched anything under it. When
  tt-git was started in a subfolder, that folder comes first, marked `current folder`.
- **Matching** ignores case. Entries that contain what you typed come first, then entries that only
  match it as a sequence of letters, so `apcmp` still finds `app/components/`.
- **Deleted files** aren't in the list, since only files that still exist are. If nothing matches on
  the File tab, <kbd>enter</kbd> uses what you typed as the path, so you can still see the history of
  a file that's gone. The popup says so: `no matches · enter shows commits that changed …`.

When a filter is set, the first entry on its tab is **Any author** or **Any file**, which clears just
that part. To clear the whole filter, close details and press <kbd>esc</kbd> in the graph.

<Screenshot name="graph-filter-folder" alt="The graph filtered to a folder, with the filter shown in its title" />

A file filter keeps the lanes joined up: each commit links to the nearest earlier commit that also
touched the path, so you still get a readable graph. An author filter can't do that, so each run of
one person's commits is its own short line. Renames aren't followed. If no commits match, the graph
says `no commits match the filter (f or / to change it, esc to clear it)`.

## Filtering by message

<Screenshot name="graph-filter-message" alt="The Filter commits by message prompt with its search-in choices and row of presets" />

Press <kbd>/</kbd> to open **Filter commits by message**. Type a regex, press <kbd>enter</kbd>, and
the graph shows only the commits whose subject (the first line of the message) matches it. It's
built for [conventional commit](https://www.conventionalcommits.org/) prefixes: `^feat` shows the
features, `^(fix|perf)` the fixes and speedups, `^docs\(graph\)` the graph's docs.

Press <kbd>ctrl+t</kbd> in the prompt to change what the regex searches. The top row,
`Search in: Subject · Whole message · Diff`, underlines the choice, and each <kbd>ctrl+t</kbd> moves
on to the next, round from **Diff** to **Subject**:

| Search in | Finds the commits whose |
|---|---|
| **Subject** | first line matches. The default. |
| **Whole message** | message matches anywhere: subject, body or trailers. `^` and `$` match at the start and end of each line, so `^Co-authored-by: Ann` finds Ann's pairings and `^feat` still finds `feat:` subjects. |
| **Diff** | changes add or remove a line that matches, as `git log -G` finds them. `parse_body` finds where a function came and went. |

<Screenshot name="graph-filter-diff" alt="The graph filtered to the commits whose diff adds or removes a match for notification, with diff /notification in its title" />

<Steps>

1. Press <kbd>/</kbd>.
2. Type a regex, or press <kbd>tab</kbd> to fill in the first preset. <kbd>tab</kbd> again moves on
   to the next one and <kbd>shift+tab</kbd> back, round from the last to the first. The preset in the
   box is underlined in the row above it.
3. Edit it if you like, then press <kbd>enter</kbd>. <kbd>ctrl+w</kbd> deletes the word before the
   cursor, as in a shell, so it clears a regex like `^(fix|perf)` in one go; <kbd>ctrl+u</kbd> clears
   everything.

</Steps>

- **Presets** are the 8 subject prefixes the repository uses most, in its newest 1000 loaded
  commits, most used first. A prefix is the first word of a subject followed by `:`, with an optional
  `(scope)` and `!` in between, so `feat(blame)!: Step through commits` counts for `^feat`. Emoji
  or `:shortcode:`s before it stay in the preset: `🤖 feat: Add it` counts for `^🤖 feat`. Case
  doesn't matter: `Fix:` and `fix:` both count for `^fix`. They're worked out from the whole graph
  and stay the same while it's filtered. A repository with no such prefixes has no presets. Set a
  fixed list with [`message_presets`](/configuration/#graph) under `[graph]`, for every repository
  in `config.toml` or for one in its [`.tt-git.toml`](/configuration/#per-repository-config).
- **Case** is ignored unless the regex has a capital letter, as in
  [blame's search](/panes/blame/). `fix` finds `Fix typo`; `Fix` doesn't find `fix: typo`.
- **Only the subject** is searched until you pick another choice, so `^feat` means the subject
  starts with `feat`, not that some line of the body does.
- **Regex syntax** is Rust's [`regex`](https://docs.rs/regex/latest/regex/#syntax), close to what
  most editors use. The line under the box says what's searched, whether it ignores case, or what's
  wrong with it. An invalid regex keeps the prompt open.
- **The diff** is searched by git, so its regex is git's POSIX extended regex: `\d` and `\b` don't
  work there, `[0-9]` does. git checks it when the graph loads, and a bad one shows git's error. A
  diff search reads every commit's changes, so on a big repository it takes a while; the title says
  `loading…` until it's done. Merge commits have no diff of their own and are never found.
- **With other filters**, a commit has to match all of them: the message, an author and a file from
  <kbd>f</kbd>, and the [folder](#narrowing-to-the-folder-you-started-in).
- **The title** shows it, with what's searched: `Graph [all · subject /^feat]`,
  `message /^Co-authored-by` or `diff /parse_body`. Press <kbd>/</kbd> again to change it; the prompt
  starts with the regex and the choice set now. Clear the box and press <kbd>enter</kbd> to drop just
  the message part (the choice goes back to **Subject**), or close details and press <kbd>esc</kbd>
  in the graph to clear the whole filter.

As with an author filter, the lanes don't join up across the commits left out.

## Acting on a commit

<Screenshot name="graph-new-branch" alt="The New branch dialog opened from the graph" />

These keys act on the selected commit:

| Key | Does |
|---|---|
| <kbd>enter</kbd> | Opens the commit fullscreen: its changed files on the left, the selected file's diff on the right. See [Details](/panes/details/#fullscreen-files-and-diff). |
| <kbd>space</kbd> | Shows or hides the commit's [details](/panes/details/). |
| <kbd>o</kbd> | Checks out the commit. See [Checking out a commit](#checking-out-a-commit). |
| <kbd>n</kbd> | Makes a new branch at the commit and switches to it. <kbd>tab</kbd> in the dialog makes it in a new [worktree](/git/worktrees/) under `.worktrees/` instead. |
| <kbd>T</kbd> | Makes a tag at the commit. <kbd>tab</kbd> in the dialog makes it annotated, and asks for a message next. See [Tags](/panes/tags/#making-a-tag). |
| <kbd>M</kbd> | Merges the commit into the current branch, after asking. |
| <kbd>r</kbd> | Rebases the current branch onto the commit, after asking. |
| <kbd>C</kbd> | Cherry-picks the commit onto the current branch, after asking. With a [range selected](#cherry-picking-several-commits), cherry-picks every commit in it. |
| <kbd>R</kbd> | Reverts the commit: a new commit that undoes it, after asking. For a merge commit it asks which parent's side to keep. See [Revert](/git/merge-rebase/#revert). |
| <kbd>v</kbd> | Starts or ends a range of commits. See [Cherry-picking several commits](#cherry-picking-several-commits). |
| <kbd>c</kbd> | Copies the full commit hash to the clipboard. |
| <kbd>A</kbd> | Asks an AI agent about the commit, or starts a ready-made request such as *Explain branch*. See [Agent actions](/git/agents/). |

For <kbd>M</kbd> and <kbd>r</kbd>, if a branch points at the commit, tt-git uses the branch name
(`Merge feature into the current branch?`); otherwise it uses the hash. If a merge, rebase or
cherry-pick or revert stops on a conflict, see [Merge, rebase, cherry-pick and revert](/git/merge-rebase/).

Copying uses your terminal's clipboard support (OSC 52), so it also works over SSH.

### Cherry-picking several commits

<kbd>v</kbd> starts a range at the selected commit. Move with <kbd>j</kbd>
<kbd>k</kbd> (or click a row) to extend it: every commit in the range is
highlighted, and the title shows how many are selected (`· 3 selected`).
<kbd>v</kbd> again or <kbd>esc</kbd> ends the range.

<Screenshot name="graph-cherry-pick-range" alt="Three commits selected as a range in the graph, with the Cherry-pick range confirmation open" />

<kbd>C</kbd> with a range asks **Cherry-pick range**, naming the oldest and
newest commit, then applies them all onto the current branch, oldest first,
in one `git cherry-pick`. If one stops on a conflict, resolve it and continue
from the status pane: the rest of the range applies after it. Aborting puts
the branch back as it was before the whole range. See
[Merge, rebase and cherry-pick](/git/merge-rebase/#cherry-pick).

A range that includes a merge commit is refused, since cherry-pick can't
apply merges. The range stays through refreshes, and ends once the
cherry-pick runs.

### Checking out a commit

<kbd>o</kbd> checks out the selected commit:

- If a local branch points at it, tt-git switches to that branch
  (`git switch <name>`), so you don't end up on a detached HEAD where `main`
  already is. With several, the first alphabetically wins.
- Otherwise it checks out the commit itself with HEAD detached
  (`git switch --detach <commit>`). The graph shows ` HEAD ` on it.
- If HEAD is already there, tt-git says so and does nothing.

With uncommitted changes, tt-git asks first: **Uncommitted changes** says how
many files have changes and offers to stash them. <kbd>y</kbd> stashes
everything, untracked files included, then checks out; the changes wait on
the [Stash tab](/panes/stash/) to pop back later. <kbd>n</kbd> or
<kbd>esc</kbd> leaves everything as it was. If the checkout still fails after
stashing, tt-git pops the stash straight back so your changes aren't left
behind.

To check out a branch by name, use the [Branches](/panes/branches/#checking-out) pane.

## Zoom

Press <kbd>+</kbd> to make the graph fill the screen, and <kbd>+</kbd> again to go back. With the graph
fullscreen, <kbd>space</kbd> opens details below it at full width.

<Screenshot name="graph-zoom" alt="The graph zoomed to fill the screen with details open below it" />

## Large histories

The graph loads 1,000 commits at a time while `git log` is still running, so the first rows appear
straight away. It loads up to 20,000 commits (`max_commits`), and when you scroll within 200 commits
of the end, it loads the next batch. On a refresh the old rows stay on screen until the new ones
arrive, so the graph never flashes empty. A fetch that brings nothing new doesn't reload it at all.

See [How tt-git uses git](/reference/how-it-works/#graph) for the details, and
[Memory and speed](/reference/performance/) for what this costs on a large repository.
