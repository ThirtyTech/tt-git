Blame shows a file line by line with the commit that last changed each line: when, who and why.
From any line you can open its commit, or step back to the file as it was before that commit, to
follow a line through its history. Open it with <kbd>b</kbd> on a file in the
[status pane](/panes/status/) or in [details](/panes/details/).

<Screenshot name="blame-overview" alt="Blame open fullscreen, with an age stripe, author and commit beside each line of code" />

## Opening blame

<Steps>

1. Select a file in the status pane, or scroll a commit's diff in details to the file you want.
2. Press <kbd>b</kbd>. Blame opens fullscreen.
3. When you're done, press <kbd>esc</kbd> to go back to exactly what you came from.

</Steps>

What gets blamed depends on where you press <kbd>b</kbd>:

| Where | Blames |
|---|---|
| Status pane | The selected file in your working tree, from the top |
| Details, showing a commit (or the commit fullscreen, or its changed files) | The file in view as of that commit, at the line at the top of the diff |
| Details, showing a working-tree diff | The file in your working tree, at the line at the top of the diff |

A file deleted from the working tree is blamed as it was in `HEAD`. A file a commit deleted is
blamed as it was just before that commit (`<commit>^`).

An untracked file, or one you've added but never committed, has no history to show. The help bar
says so instead:

```text
src/new.rs isn't committed yet: nothing to blame
```

Blame runs in the background, and the title says `loading…` until it arrives. Blaming the working
tree takes a snapshot when it opens: it doesn't update as you edit the file. Press <kbd>esc</kbd>
and <kbd>b</kbd> again to see your latest changes.

## The title

The title names the file and the version you're looking at, then what <kbd>esc</kbd> goes back to,
then where you are:

```text
Blame src/app.rs at working tree  ‹ Status 120/348
```

The version is `working tree`, `HEAD`, a short commit id such as `59f1c2a`, or `59f1c2a^` once
you've stepped back past a commit. After you [step back](#stepping-back), the `‹ …` names the newer
version <kbd>]</kbd> returns to instead. While <kbd>{'{'}</kbd> or <kbd>{'}'}</kbd> looks for the
next version, it says `previous commit` or `next commit`.

At the right of the top border is when that version of the file was made: the date of the last
commit that changed it, at or before the version you're looking at.

```text
changed 2026-10-17 01:30 PM (3w ago)
```

It changes as you step back and forward, so you can see how old each version is. In the working
tree, `+ uncommitted changes` follows it when some lines aren't committed yet.

At the very end, after a `·`, blame says whether you're looking at the latest version of the file:

| It says | When |
|---|---|
| `latest`, in green | The file is the same as in `HEAD`: no commit since has changed it. The working tree is always the latest. |
| `3 newer commits`, in yellow | That many commits between this version and `HEAD` have changed the file, counting a rename and the commits under its new name. |
| `not on HEAD`, in yellow | The version is from a commit that isn't in `HEAD`'s history, such as one on another branch, and the file differs from `HEAD`'s. |

```text
changed 2026-10-17 01:30 PM (3w ago) · 2 newer commits
```

So after you [step back](#stepping-back), or open blame from an older commit in the graph, you can
see how far you are from the latest at a glance. When the pane is too narrow for the title and all
of this, the date is left out first, and `latest` or the count stays.

## Reading a line

Each line reads right to left from the code: when it changed, who changed it, and why.

<Screenshot name="blame-gutter" alt="Close-up of the blame gutter: commit and summary, author, age and the age stripe beside the code" />

- **When**: next to the line number, a stripe (`▌`) colored by age, from hot orange for the newest
  commits in this file to cold blue for the oldest. Then the age, like `23h` or `2w`, or the local
  date and time, like `2026-10-17 01:30 PM`; <kbd>t</kbd> switches between them.
- **Who**: the author, on every line, next to the date. Each author in the file gets a color of
  their own, so you can see whose lines are whose at a glance. There are 16 colors; two authors
  share one only when more than 16 people wrote the file. An author usually keeps their color from
  file to file, but can get a different one where it would clash with someone else's.
- **Why**: the short commit id and the commit's summary. These show only on the first line of each
  run of lines from the same commit, so a block someone wrote in one go reads as one block. They're
  left out when the pane is narrower than 100 columns.

Lines you haven't committed yet show `You`, a green stripe and `Not committed yet`.

The code itself is [colored by language](/panes/details/#code-colors), the whole file at once, so a
block comment or a long string spanning several lines is colored right.

The selected line is highlighted. Every other line from the same commit gets a softer highlight, so
you can see everything that commit touched in the file.

Move with <kbd>j</kbd> <kbd>k</kbd>, a page at a time with <kbd>ctrl+d</kbd> <kbd>ctrl+u</kbd>, and
to the top or bottom with <kbd>g</kbd> <kbd>G</kbd>. Click a line to select it, or double-click it to open its commit as
<kbd>enter</kbd> does; the mouse wheel moves too.

## Going to a line

Press <kbd>ctrl+g</kbd>, as in VS Code. A `Go to line (1-348)` box opens over blame. Type the line
number and press <kbd>enter</kbd>; <kbd>esc</kbd> closes the box without moving. A number past the
end goes to the last line. If the line is off screen, blame scrolls it a third of the way down.

If you're used to vim, these work too:

- **A count before <kbd>G</kbd> or <kbd>g</kbd>**: type `42` then <kbd>G</kbd> to go to line 42.
  While you type, the title shows `go to 42…` after where you are. <kbd>esc</kbd> drops the count
  without leaving blame, and any other key uses it up.
- **A count before <kbd>j</kbd> or <kbd>k</kbd>** moves that many lines: `5j` goes down five.
- **`:42` and <kbd>enter</kbd>**: <kbd>:</kbd> opens the [command palette](/git/palette/) as
  usual, and in blame typing a number there turns the list into a single `Go to line 42` entry.

While blame is focused, the digits count lines, so <kbd>1</kbd> to <kbd>4</kbd> don't switch panes.
Use <kbd>esc</kbd> or <kbd>tab</kbd> to leave.

## Searching the code

Press <kbd>/</kbd> and type a regular expression to find a line. The search shows in the title as
you type, and blame jumps to the first matching line from where you started, going round to the top
when there's none below:

```text
Blame src/app.rs at working tree  ‹ Status 120/348 /fn draw█ 2/5
```

`2/5` says you're on the second of five matching lines. Every match is highlighted in the code.

<Screenshot name="blame-search" alt="Blame searching for res\.status, on the second of four matching lines, each match highlighted" />

- <kbd>enter</kbd> keeps the search. The title still shows it, and the keys work as usual again.
- <kbd>esc</kbd> drops the search and goes back to the line you were on.
- <kbd>backspace</kbd> deletes a character.

Then <kbd>n</kbd> goes to the next matching line and <kbd>N</kbd> to the previous one. Past the
last match they go round to the first, and the help bar says `search wrapped to the top` (or
`to the bottom`).

The search ignores case unless the pattern has a capital letter: `todo` finds `TODO` and `Todo`,
but `Todo` finds only `Todo`. Put `(?i)` at the start to ignore case anyway, or `(?-i)` to match it
anyway. The syntax is the [Rust `regex` crate's](https://docs.rs/regex/latest/regex/#syntax), much
like other languages' regular expressions without look-around or backreferences. Each line is
searched on its own.

While the pattern doesn't make a valid regex, for example `foo(`, the title says `invalid regex`
and the selection stays put. <kbd>enter</kbd> on it drops the search and the help bar says why.
When nothing matches, the title says `no match` and <kbd>n</kbd> says `no match for /foo`.

The search stays when you [step back](#stepping-back) or forward again, and finds its matches in
the version you're looking at.

## The commit behind a line

<Screenshot name="blame-commit" alt="The commit behind a blamed line, opened fullscreen with the line marked in its diff" />

Press <kbd>enter</kbd> to open the selected line's commit fullscreen, the same way
[<kbd>enter</kbd> in the graph](/panes/details/#fullscreen-files-and-diff) does. Every file the
commit changed is listed on the left, with this file selected, and the diff is scrolled to your
line and marks it `◂ line 42 in blame`. <kbd>j</kbd> <kbd>k</kbd> show the commit's other files.

Press <kbd>esc</kbd> to come back to blame exactly as you left it: the same version, line, scroll and
details.

On a line that isn't committed yet, there's no commit to open, and the help bar says
`this line isn't committed yet: there's no commit to open`.

### Blaming from the commit

In a commit you opened from blame, <kbd>b</kbd> blames whichever of its files you're looking at, as
of that commit. You can keep going: open a line's commit, blame another file there, open a commit
from that, and so on. The views stack, and each <kbd>esc</kbd> goes back one level. The `‹ …` in
the title names the level below, for example:

1. Blame of `client.ts` at the working tree, on line 33.
2. <kbd>enter</kbd>: the commit that last changed line 33.
3. <kbd>b</kbd> on `NotificationBell.tsx` in that commit: its blame at that commit.

From there, <kbd>esc</kbd> goes back to the commit, and <kbd>esc</kbd> again to the blame of
`client.ts` on line 33. Focusing another pane drops the whole stack.

## Stepping back

<Screenshot name="blame-step-back" alt="Blame after stepping back, showing the file as it was before the selected line's commit" />

The commit that last changed a line often just moved it or reformatted it. To see what was there
before, press <kbd>[</kbd>. Blame shows the file as it was just before the selected line's commit,
following it through a rename. Press <kbd>[</kbd> again to go further back.

Blame stays on the same line of code as you step. It compares the two versions' text, so when
lines were added or removed above it, the selection moves with the line rather than staying on
its old number. A line the commit changed lands on the most similar line it replaced. A line the
commit added lands where it was added. The selected line keeps its row on screen. While the older
version loads, the newer one stays on screen, so you don't lose your place.

Press <kbd>]</kbd> to go forward again, to the newer version you stepped back from. Blame follows
the selected line forward the same way, so a line you moved to in the older version is still
selected in the newer one. At the newest one, the help bar says `this is the newest version`.

On a line that isn't committed yet, <kbd>[</kbd> steps back to `HEAD`. If the commit added the file,
there's nothing earlier to show:

```text
59f1c2a added src/app.rs: there's nothing before it
```

### One commit of the file at a time

<kbd>[</kbd> jumps straight to before the selected line's commit, past every commit that changed
other lines. To walk the file's history one commit at a time instead, press <kbd>{'{'}</kbd>. It
shows the file as it was before the newest commit that changed it, whichever lines that commit
touched, following renames. From a working tree with uncommitted changes to the file, the first
<kbd>{'{'}</kbd> goes to `HEAD`. The title names each version by its commit, such as `3a9c0e1`.

Press <kbd>{'}'}</kbd> to go forward one commit of the file, toward the newer version below it in
the title's `‹ …`. When you got here with <kbd>[</kbd>, <kbd>{'}'}</kbd> stops at each commit
<kbd>[</kbd> jumped over. Once the next version is the one below, <kbd>{'}'}</kbd> goes back to it,
the same as <kbd>]</kbd>.

Both keep the selected line by its text and on its row, as <kbd>[</kbd> and <kbd>]</kbd> do. At the
first commit of the file, <kbd>{'{'}</kbd> says:

```text
no older commit changed src/app.rs
```

At the version you opened, <kbd>{'}'}</kbd> says `this is the newest version`.

<Aside type="tip">
  If the repository has a `.git-blame-ignore-revs` file at its root, blame skips the commits listed
  in it, such as a big reformat, and shows the commit before them instead. See
  [How tt-git uses git](/reference/how-it-works/#blame).
</Aside>

## Dates

Press <kbd>t</kbd> to switch between ages (`23h`, `2w`) and the local date and time
(`2026-10-17 01:30 PM`). It's the same setting as <kbd>t</kbd> in the [graph](/panes/graph/):
switching in one switches both. Which one tt-git starts with is
[`graph.dates`](/configuration/#graph) in your config.

## Commit details

<Screenshot name="blame-details" alt="Blame with the selected line's commit details shown below the code" />

Press <kbd>space</kbd> to show the selected line's commit below the code, and again to hide it. It
shows:

- the commit's subject and short id,
- the author and their email,
- the date and time, with its age,
- how many lines in this file come from that commit,
- and the rest of the commit message.

The details follow the selection as you move.

## Copying and editing

- <kbd>c</kbd> copies the selected line's full commit hash. On a line that isn't committed yet, the
  help bar says `this line isn't committed yet`.
- <kbd>e</kbd> opens the file in your editor at the selected line. When the version you're looking
  at isn't in your working tree, tt-git opens a read-only copy of it, the same way
  [<kbd>e</kbd> in details](/panes/details/#opening-a-file-in-your-editor) does.

## Keys

| Key | Does |
|---|---|
| <kbd>j</kbd> <kbd>k</kbd> | Next / previous line |
| <kbd>ctrl+d</kbd> <kbd>ctrl+u</kbd> | Page down / up |
| <kbd>g</kbd> <kbd>G</kbd> | Top / bottom |
| <kbd>ctrl+g</kbd> | Go to a line by number |
| `42` <kbd>G</kbd> | Go to line 42 (vim style; `5j` moves down five) |
| <kbd>enter</kbd> | Open the line's commit fullscreen |
| <kbd>space</kbd> | Show / hide the line's commit details |
| <kbd>[</kbd> | Step back past the line's commit |
| <kbd>]</kbd> | Forward again |
| <kbd>{'{'}</kbd> <kbd>{'}'}</kbd> | Back / forward one commit of the file |
| <kbd>/</kbd> | Search the code with a regex |
| <kbd>n</kbd> <kbd>N</kbd> | Next / previous matching line |
| <kbd>t</kbd> | Ages ↔ dates and times |
| <kbd>e</kbd> | Open the file in your editor at the line |
| <kbd>c</kbd> | Copy the line's commit hash |
| <kbd>esc</kbd> | Back to where you opened blame |

In a commit opened from blame, <kbd>b</kbd> blames the file in view and <kbd>esc</kbd> comes back.

A click selects a line, a double-click opens its commit and the mouse wheel moves. To change these keys, use the `blame` context in
[Key bindings](/configuration/keys/).
